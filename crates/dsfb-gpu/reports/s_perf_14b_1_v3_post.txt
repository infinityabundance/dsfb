------------------------------------------------------------------------
 v3 design + sweep methodology
------------------------------------------------------------------------

v3 was the panel-required tile-size sweep to test whether ANY
tile size beats Path 1a (and where v2's 2 KB hard-coded tile
sat on the curve).

Mechanical changes shipped (all 4 retained as building blocks):
  1. v2 streaming_blockcoop kernel parameterised on tile_bytes
     (was constexpr 2048; now runtime parameter).
  2. New FFI entry `dsfb_gpu_compact_densor_root_streaming_sweep_time`
     wraps the streaming kernel with cudaEvent_t bracketing.
  3. New FFI entry `dsfb_gpu_compact_densor_root_path1a_sweep_time`
     does the same for the Path 1a kernel — apples-to-apples
     comparator at the same per-stage shapes.
  4. Rust test `tests/s_perf_14b_1_v3_tile_sweep.rs` runs both
     kernels at all four production stage shapes (residual /
     sign / detector-compact-pack / consensus) across six tile
     sizes (1 KiB / 2 KiB / 4 KiB / 8 KiB / 16 KiB / 32 KiB).

Sweep workload shape (matches canonical 256×4096 K=1 D64):
  residual : n_chunks=1024  (16 MB / 16 KB chunk)
  sign     : n_chunks=1280  (20 MB / 16 KB chunk)
  detector : n_chunks=1152  (18 B/cell compact pack, NOT 264 B wide)
  consensus: n_chunks=2048  (32 MB / 16 KB chunk)

------------------------------------------------------------------------
 Harness sweep result (apparent 45.6 % total win — SEE THE CAVEAT)
------------------------------------------------------------------------

cudaEvent_t timing (4 warmup + 32 timed iters per cell):

  stage     | Path 1a (ns) | best streaming tile | streaming (ns) | per-stage Δ
  ----------+--------------+---------------------+----------------+----------------------
  residual  |  4,317,599   | 32 KiB              |    819,678     |  -3,497,921 (-81.0 %)
  sign      |    937,222   |  8 KiB              |    958,486     |     +21,264  (+2.3 %)
  detector  |    848,671   | 32 KiB              |    856,480     |      +7,809  (+0.9 %)
  consensus |  1,516,736   | 32 KiB              |  1,513,952     |      -2,784  (-0.2 %)

  TOTAL per-dispatch (sum of 4 stages, best tile per stage):
    Path 1a  : 7,620,228 ns (7.620 ms)
    Streaming: 4,148,596 ns (4.149 ms)
    Δ        : -3,471,632 ns (-45.6 %)

The harness verdict was "streaming kernel ADMITTED at tile=32K".
This turned out to be misleading. See production ROOF below.

The residual stage Path 1a number (4.3 ms) is wildly inflated
relative to production-warmed Path 1a (~925 µs per launch).
Diagnosis: the standalone harness allocates a fresh per-call
scratch buffer (via cudaMalloc inside the FFI entry point); the
first cudaMemset + first kernel access pay a one-time cache-miss
cost that 4 warmup iterations do not fully absorb at the smallest
stage. Production workspaces persist across the entire 7-iter
bench loop; their scratch stays L2-warm.

The streaming kernel doesn't touch scratch at all → it doesn't
pay that cold-cache penalty in the standalone harness → it
appears to win by 45.6 % overall.

**v3 CADENCE VIOLATION (panel-recorded 2026-05-19)**: the sudo
POST ROOF was run ONCE, not multiple times per the panel-locked
HARD-ENFORCEMENT cadence ("you will do nsight and GB/s benchmark

noise variance on per-kernel ncu is much tighter than bench but
not zero. **v3 is NOT closed; the v4 stage-adaptive selector
campaign is the active next move.**

v4 thesis: streaming may win at SOME stages while losing at
others. Path 1a is the safety baseline; each stage switches to
streaming ONLY if production sudo ROOF (×5 invocations per
variant) proves streaming beats Path 1a at that stage. See
plan-file v4 section + the panel-locked PROMOTE-or-EXHAUSTED gate.

The improvement vs v2 (956 vs 1008 µs, -5.2 %) confirms the
tile-size sweep's directional finding (larger tiles reduce sync
count and help streaming), but the gain doesn't close the gap
to Path 1a's one-shot SHA over L2-resident scratch.

------------------------------------------------------------------------
 What the v3 sweep teaches (panel-recorded)
------------------------------------------------------------------------

The compact_densor_root layer's per-call wall under the v1
digest contract has the following structure:

  Path 1a: cooperative scratch write (~570 KB at consensus
           stage) + thread-0 one-shot SHA over L2-warmed
           scratch. Per launch: ~925 µs (pinned).

  Path 1b v2 (2 KiB tile): cooperative shared-tile load + 64
           __syncthreads barriers per launch + thread-0
           streaming SHA per tile. Per launch: ~1008 µs.

  Path 1b v3 (32 KiB tile): same with 4 barriers per launch
           instead of 64 (16× fewer barriers). Per launch:
           ~956 µs.

  Tile sweep proves the barrier-count hypothesis: tiles
  4 KiB → 32 KiB each shave ~3-10 % off v2's wall, with
  diminishing returns past 16 KiB. But the asymptotic floor
  (32 KiB) is still +3.3 % above Path 1a.

The irreducible v3 overhead vs Path 1a is the streaming SHA
update's per-call overhead × n_tiles per launch, plus a small
shared-memory-vs-L2 read-latency delta that favours L2 for
the read-once / write-once / read-once pattern Path 1a uses.

The remaining lever inside the v1 contract would be a
SHA-256 implementation rewrite to operate on shared-memory
64-byte blocks without per-block function-call overhead.
That is a bounded optimisation; the bigger system-level wall
lives in detector_motif_fused (1.32 ms @ 91 % L2) and
consensus_axis5_fused (0.40 ms @ 88 % L2) — both ~2× the
compact_densor_root layer's total. Future S-PERF.x sub-legs
should target those memory-bound kernels.
