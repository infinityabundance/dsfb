      finalize sequence absorbs bytes directly from global into
      the SHA-256 state without staging through a scratch buffer.

------------------------------------------------------------------------
 CompactDensorDigestV1 byte-stream metadata (Step 0 audit deliverable)
------------------------------------------------------------------------

The streaming SHA-256 path MUST consume bytes in this exact
order to produce byte-identical roots. Sourced from
cuda/kernels.cu at HEAD 6233622.

Header (44 bytes per root invocation):

  [ 0..28) "DSFB_STAGE_COMPACT_DENSOR_V1"  (28 B domain separator;
                                            canonical header bytes
                                            per S-PERF.10 contract)
  [28..32) fold_factor    u32 LE = 256     (panel-locked
                                            S-PERF.12 FOLD_FACTOR)
  [32..36) stage_id       u32 LE ∈ {0=residual,
                                    1=sign,
                                    2=detector,
                                    3=consensus}
  [36..40) chunk_size     u32 LE           (per-stage; from contract)
  [40..44) n_chunks       u32 LE           (per-stage; from launch
                                            — ceil(stage_bytes /
                                            chunk_size))

Body (n_chunks × 32 bytes per root invocation):

  leaf[0]  : 32 B SHA-256 of chunk 0 (already pre-computed
             by compact_densor_digest_v1_leaf_kernel and
             stored in d_compact_densor_leaves global arena)
  leaf[1]  : 32 B SHA-256 of chunk 1
  ...
  leaf[n-1]: 32 B SHA-256 of chunk n-1

Total bytes streamed per root invocation:
  44 + n_chunks × 32 bytes

Canonical leaf ordering:
  catalog-major × chunk-index-minor
  (each catalog's leaves are contiguous; within a catalog,
  chunks are sequential ascending. Per-stage n_chunks scales
  with the stage's payload size: residual / sign / detector /
  consensus chunks per stage differ because their per-cell
  payloads differ.)

Streaming SHA-256 path requirements:

  1. Process header bytes FIRST in canonical order (28-byte
     domain string, then 4 u32 LE fields).
  2. Process leaf bytes in canonical leaf order (no
     re-ordering, no skipping, no duplication).
  3. SHA-256 init/update/finalize sequence MUST handle
     tail-block padding (when total bytes mod 64 != 0).
  4. The total byte count (44 + n_chunks × 32) MUST match
     the one-shot path EXACTLY (off-by-one in the trailing
     length encoding produces a different root).

Cross-validation requirement (S-PERF.14b.1 Step 1):

  Before the root kernel rewrite, add a known-vector
  cross-validation test that runs both dsfb_sha256_device
  (one-shot) and the new streaming init/update/finalize
  helpers on three inputs:
    - empty (0 bytes)              — pure padding edge case
    - 55 bytes                     — single SHA block tail
    - 64 KB (64 × 1024)            — multi-block + clean tail
  Both implementations MUST produce byte-identical 32-byte
  digests for all three inputs. This validates the streaming
  primitives before they're invoked from the root kernel.

Root cause analysis:

  The Step 0d byte-counter prediction was correct: streaming SHA
  eliminates the scratch round-trip (DRAM 1.70 → 0.58 %; L1
  ST/LD ratio drops as expected). But the streaming kernel's
  1-thread-per-block launch geometry ALSO eliminated Path 1a's
  256-thread cooperative byte-load parallelism. Net result:

    Path 1a phases (256 threads cooperatively load, 1 thread SHA):
      Phase 1 (header write):      ~0 µs (thread 0 only)
      Phase 2 (cooperative load):  ~50 µs (256 threads bulk-copy in parallel,
                                            then __syncthreads)
      Phase 3 (serial SHA):       ~875 µs (1 thread reads scratch → SHA)
      TOTAL:                       ~925 µs

    Path 1b v1 (1 thread streams + SHA):
      Phase 1 (header in registers): ~0 µs
      Phase 2+3 (1 thread reads bytes ONE AT A TIME from global
                 and feeds streaming SHA):
                                   ~2,860 µs
      The "byte-at-a-time" per-thread streaming update in
      dsfb_sha256_update loses ~3× to coalesced parallel reads
      from Path 1a's cooperative load.

  The byte-counter trace was right about WHERE the wall lives
  (scratch round-trip), but the FIX needed to preserve Path 1a's
  parallel byte-load phase. My Path 1b v1 traded one slow path
  (parallel load + serial SHA + scratch round-trip) for another
  slow path (serial load + serial SHA, no scratch).

------------------------------------------------------------------------
 Lesson learned for future Path 1b v2 (panel-recorded)
------------------------------------------------------------------------

The next attempt MUST preserve Path 1a's 256-thread cooperative
byte-load parallelism while eliminating the global-scratch
round-trip. Proposed Path 1b v2 design:

  - Use SHARED memory as the staging buffer (not global scratch).
    Shared mem per block on RTX 4080 SUPER is up to ~100 KB —
    enough for canonical's ~64 KB leaves per stage.
  - 256 threads cooperatively load leaves from global into
    shared memory (preserves Path 1a's parallel byte movement,
    but writes to L1-equivalent shared instead of L2-resident
    global scratch).
  - __syncthreads().
  - Thread 0 streams bytes from shared into the SHA-256
    streaming state (eliminates the L2-resident global-scratch
    round-trip; reads from shared are 1-cycle, much faster than
    reading from L2).
  - Output 32-B root.

  Expected vs measured:
    Path 1a wall ≈ 925 µs (parallel load + serial SHA from L2 scratch)
    Path 1b v2 ≈ 900 µs (parallel load + serial SHA from shared)
                projected ~20-30 µs savings; bounded by the
                serial-SHA compute floor (which is the bulk of
                the 925 µs).

  Honest projection: Path 1b v2 might land 925 → 850-900 µs
  (~3-8% per-invocation, ~0.1-0.3 ms total dispatch). The
  bulk of the kernel's 925 µs is structurally bounded by
  thread-0 SHA-256 compute, NOT memory; only a parallel-SHA
  redesign (CompactDensorDigestV2) could break that floor,
  and V2 is panel-forbidden under the digest-mode non-aliasing
  law.

  Recommendation: Path 1b v2 is a small marginal lever; the
  remaining device wall post-S-PERF.15.d is dominated by
  kernels that ARE memory-bound (detector_motif_fused 1.32 ms
  @ 91 % L2 / consensus_axis5_fused 397 µs @ 88 % L2). Future
  S-PERF.x sub-legs should target those before re-attempting
  the compact_densor_root layer.
